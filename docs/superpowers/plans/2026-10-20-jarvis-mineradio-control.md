# Jarvis–Mineradio Voice Control Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Jarvis understand natural voice requests and control a local Mineradio instance through a versioned, authenticated Windows named-pipe bridge.

**Architecture:** Jarvis remains the voice/Codex/tool owner and hosts a current-user Windows named-pipe server. Mineradio receives a one-time endpoint/token pair through normal launch arguments or Electron's `second-instance` event and connects as a client. Jarvis exposes allowlisted Mineradio actions as dynamic Codex tools, and Mineradio routes accepted actions into its existing main-process/renderer playback APIs.

**Tech Stack:** TypeScript, Electron main processes, Node `net` named-pipe streams on Windows, newline-delimited JSON, Codex app-server dynamic tools, Mineradio JavaScript/Electron IPC, `tsx --test`.

## Global Constraints

- Keep all work local; do not push to a remote repository.
- Do not expose arbitrary shell, JavaScript, URLs, file paths, or renderer commands through the bridge.
- Only the current interactive Windows user may connect; require a per-launch random handshake token generated by Jarvis and passed only to the launched/forwarded Mineradio instance.
- Bound frames, request timeouts, query lengths, and volume values.
- A spoken success response must be based on a successful Mineradio response, never on request dispatch alone.
- Keep the first release to app open/focus, playback state, play/pause/resume, previous/next, volume, and search-and-play.
- Preserve the existing local, Doubao, and future Codex Voice paths by keeping the bridge below the voice-provider layer.

### Task 1: Define and test the shared Mineradio bridge protocol in Jarvis

**Files:**
- Create: `electron/mineradio-protocol.ts`
- Test: `tests/windows-mineradio-protocol.test.ts`

**Interfaces:**
- Produces `MINERADIO_PROTOCOL_VERSION`, `MINERADIO_PIPE_NAME`, `MINERADIO_MAX_FRAME_BYTES`, action/result types, `encodeFrame(value)`, `decodeFrame(line)`, `isAllowedAction(action)`, and `validateRequest(value)`.
- Handshake shape: `{ version: 1, type: "hello", token: string }`; after authentication the server sends `{ version: 1, type: "ready" }`.
- Request shape: `{ version: 1, type: "request", id: string, action: AllowedAction, payload: object }`.
- Response shape: `{ version: 1, type: "response", id: string, ok: boolean, result?: object, error?: { code: string, message: string } }`.
- Event shape: `{ version: 1, type: "event", event: string, revision: number, payload: object }`.

- [ ] **Step 1: Write failing protocol tests**

```ts
test('encodes and decodes bounded request frames', () => {
  const line = encodeFrame({ version: 1, type: 'request', id: 'r1', action: 'player.pause', payload: {} });
  assert.deepEqual(decodeFrame(line), JSON.parse(line));
});

test('rejects unknown actions, malformed frames, and oversized frames', () => {
  assert.throws(() => validateRequest({ version: 1, type: 'request', id: 'x', action: 'exec.shell', payload: {} }));
  assert.throws(() => decodeFrame('{bad'));
  assert.throws(() => encodeFrame({ data: 'x'.repeat(MINERADIO_MAX_FRAME_BYTES) }));
});
```
